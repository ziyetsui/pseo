## F1 · 公开构建站点 URL 门禁缺口（High）

**Evidence：** `frontend/src/lib/catalog/config.ts:10` 只校验 API 与 revision；`frontend/src/app/robots.ts:6` 缺 `FRONTEND_SITE_URL` 就返回全站 Disallow。`frontend/README.md:22` 的 public 构建示例没有设置它。本轮用合成输入调用 config 已复现缺值仍被接受；未声称当前生产环境缺值。

**Impact：** 按该构建路径发布时，已获索引资格的内容会被robots阻止抓取；meta index 和 sitemap 无法补救。Google需要访问页面才能读取页面指令。[Google抓取与noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing)

**Fix（工程建议，未应用）：** 将发布用canonical origin设为必填并验证。可在公开发布配置校验中加入以下最小门禁，README同步声明该变量；进一步与snapshot提供的canonical origin校验一致。不要填localhost或猜测真实域名。

```ts
const rawSite = environment.FRONTEND_SITE_URL;
if (!rawSite) throw new Error('FRONTEND_SITE_URL is required for public publication');
const site = new URL(rawSite);
if (site.protocol !== 'https:' || site.username || site.password ||
    site.pathname !== '/' || site.search || site.hash) {
  throw new Error('FRONTEND_SITE_URL must be an HTTPS origin');
}
```

这段代码针对发布意图；public-api本地验收应有显式隔离约定。验证：缺值/非HTTPS/跨canonical origin构建应拒绝；合法配置下已批准URL可抓取，fixture继续禁索引。

## F2 · Prompt hreflang没有忠实投影API（Medium）

**Evidence：** `frontend/src/site/metadata.ts:15` 读取entity的hreflang，却把Prompt的语言URL按env重建。`types.ts:78` 未声明Prompt SEO的hreflang，`public.ts:33`实际已经传入detail.seo。内存复现：没有SITE_URL时所有语言关系丢失；给不同origin时canonical保留API域名、hreflang变成另一个域名。

**Impact：** 破坏同一内容的语言关系一致性；不能保证互相返回的已批准locale URL。[Google hreflang](https://developers.google.com/search/docs/specialty/international/localized-versions)

**Fix：** 给Prompt.seo显式补上 `hreflang: Record<string, string>`；public保持已验证API值，fixture设 `{}`。随后将metadata中的languages替换为：

```ts
alternates: {
  canonical: visual ? undefined : canonical,
  languages: visual ? undefined : seo?.hreflang,
}
```

验证canonical/hreflang同一事实源，已批准en/zh-CN互链；只保留事实源已有x-default，不编造缺失翻译。这不是要求当前fixture输出hreflang。

## F3 · L1/Blog索引资格与sitemap接线不一致（Medium，条件触发）

**Evidence：** `frontend/src/app/[locale]/[[...path]]/page.tsx:40` 仅匹配 `/blog/`，列表 `/blog` 落通用分支，和L1一样没有seo对象，固定noindex。compiler `infra/lib/content-pipeline.mjs:1707/1743` 在L1已批准或locale有可索引文章时会列出相应列表。`finalize-export.mjs:54` 只检查HTML存在就复制sitemap。

**Impact：** 当上述批准条件成立时，sitemap与页面的索引要求互相矛盾；当前无文章/无surface资格时的noindex仍正确。[Google sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)

**Fix：** 从同一已验证snapshot读取surface/list SEO资格，再按页面映射。API Home目前没有 `home.seo`，不能虚构该字段或直接把所有列表改index。先补导出门禁以拒绝不一致产物：在finalizer添加 `import { parse } from 'node-html-parser'`，将sitemap loc循环中的纯readFile替换为以下核对（沿用现有路径校验）：

```js
const expectedCanonical = match[1].replaceAll('&amp;', '&');
const document = parse(await readFile(path.join(out, `${pathname}.html`), 'utf8'));
const robots = document.querySelector('meta[name="robots"]')?.getAttribute('content') ?? '';
const canonical = document.querySelector('link[rel="canonical"]')?.getAttribute('href');
if (/\bnoindex\b/i.test(robots) || canonical !== expectedCanonical) {
  throw new Error(`Sitemap/HTML SEO mismatch: ${pathname}`);
}
```

正式门禁还应核对最终响应headers。验证需用有批准surface/文章的合同fixture，分别证明index匹配通过、noindex冲突失败，不能凭当前空Blog证明未来通过。

## F4 · 集合页摘要泛化、系列与版本标题重复（Medium）

**Evidence：** 当前40/74内容页使用 `Original prompts, their results, and the people who wrote them.`；Nano Banana系列与基础版本页都是 `Nano Banana prompts · Prompt Library`，GPT系列/版本同样重复。Hub、locale别名和空Blog共用 `The library · Prompt Library`。精确URL清单保存在summary.json。

**Impact：** 摘要未说明页面是模型系列、任务还是风格；系列与版本范围难区分。不是重复内容处罚的证据，也不因title只有36字符而判失败。[Google标题建议](https://developers.google.com/search/docs/appearance/title-link)、[摘要建议](https://developers.google.com/search/docs/appearance/snippet)

**Fix：** 原文Prompt和已定视觉文案保留；通过CMS受审核SEO字段定义可索引页面的title/description，metadata只投影。以下仅是待审核文案方向，**不是已修改的内容**：

| 页面 | title候选 | description候选 |
|---|---|---|
| Nano系列 | Nano Banana family prompts · Prompt Library | Browse prompts for Nano Banana, Nano Banana Pro and Nano Banana 2, with full text, source credits and available results. |
| Nano基础版本 | Nano Banana model prompts · Prompt Library | Explore prompts tagged with the original Nano Banana model, with full text and links to their source posts. |
| Beauty | Beauty prompts · Prompt Library | Browse beauty prompts by model and style, inspect available results, and open the full prompt with its source credit. |

无独立资格的系列页继续noindex。验证按route/type检查唯一语义、正文一致性；不用关键词密度阈值改写作者Prompt。

## F5 · 运营方联系与信任入口缺失（Medium，上线内容缺口）

**Evidence：** 根与zh-CN的about/contact/privacy/terms共8个URL实测404；路由清单与共享footer没有相应入口。Creators和来源X链接属于原作者，不能替代本站运营方联系方式。

**Impact：** 用户能找到作者，但不能从当前界面了解谁运营资料库或联系本站处理纠错/下架。Google鼓励清晰来源及站点背景；并非所有站点必须有四个页面才能排名。[Google可信内容指导](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

**Fix：** 运营方提供真实介绍、联系/下架渠道及实际数据处理说明，走CMS proposal与人工审核后创建路由；footer仅连接已存在且验证200的页面。联系方式可以放在About或footer，不强制再造Contact页面。隐私/条款的法律适用性本轮未判断，不自动生成Cookie同意、地址、电话或DPA承诺。验证真实链接可达且有实质内容；审核前保持此项open。

## F6 · favicon 404（Low）

**Evidence：** 本轮Lighthouse `errors-in-console`记录 `http://127.0.0.1:3000/favicon.ico` 404；Squirrel也未发现favicon。共享layout无icons元数据。

**Impact：** 浏览器缺少品牌图标，搜索favicon资格没有完整入口；不是收录阻断。[Google favicon规范](https://developers.google.com/search/docs/appearance/favicon-in-search)

**Fix：** 将批准的方形品牌图标放入 `frontend/public/favicon.svg`，在两个root layout的metadata中合并 `icons: { icon: '/favicon.svg' }`。图标必须真实存在，不先加死链接；可以同时提供favicon.ico以消除默认请求404。验证icon URL 200、正确MIME、手机/桌面浏览器图标。
