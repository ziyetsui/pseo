# 把已有页面做得更好

你发现页面过时、表现下降、相互重叠，想先修好它们。

## 输入与范围

现有页面与 revision；质量问题、来源变化或测量结果。

可单独使用，不要求已运行整套流程。读取用户指定的产物与适用项目规则；缺必需输入时先复用已有材料，只补问阻塞当前步骤的信息。默认将新产物保存到 `docs/pseo/`，用户指定位置优先。不要因使用本 skill 扩大任务、生产权限或费用范围。

## 执行

1. 先区分数据源变化、内容缺口、技术抓取问题、意图不匹配、重复内耗与正常观察延迟，避免看到流量下降就全面重写。

2. 逐页列出 URL/revision、问题、证据、拟改字段、预期观察指标及回滚。优先修复影响模板或数据管道的共性根因。

3. 源事实变化时标记依赖页面与译文待复核。保留 immutable id；必要 slug/URL 变化准备 redirect 与链接更新提案。

4. 合并或撤下可能影响已有流量和访问：先给具体影响与可审查结果，再沿宿主授权/审核流程执行。不要无证据批量删页。

5. 只更新实质变化对应时间，不通过换年份/更新时间制造新鲜度。内容变更仍走原来的草稿与审核边界。

6. 安排修复后的技术复查和同口径观察，不以内容已写好宣布效果已恢复。

## 交付与完成条件

主交付：`17-refresh-plan.md`（更新、合并与撤下提案）。记录输入版本、证据位置、实际检查、未知与阻塞。

- 提案解释为什么改、改哪里、影响哪些页面以及如何验证。
- 权利/内容审核不会因维护任务被跳过，效果判断仍等待真实数据。

若项目已有 `project.json` 进度记录，只有完成条件有证据时才更新本步骤为 complete；缺口写 blocked，未实测写 not_checked，不把个人学习勾选当工程证据。上游 revision 变化后重查受影响结论。

下一步通常是 `pseo-expand`，但以用户当前目标和真实缺口为准。未安装下一项时说明缺项；本步骤仍可独立交付，不假装调用成功。
