# 看见页面带来的效果

页面已经上线，或你想先定义怎样判断它们是否有效。

## 输入与范围

页面族清单、业务转化定义；可选 Search Console/分析平台授权导出或现有数据。

可单独使用，不要求已运行整套流程。读取用户指定的产物与适用项目规则；缺必需输入时先复用已有材料，只补问阻塞当前步骤的信息。默认将新产物保存到 `docs/pseo/`，用户指定位置优先。不要因使用本 skill 扩大任务、生产权限或费用范围。

## 执行

1. 在没有测量数据时先定义 measurement plan，而不是造报表。读取用户已有权限范围内的导出；无法接入分析平台可以从 CSV 开始。

2. 按页面族、URL、locale、发布批次与观察区间统计 eligible→deployed→discovered/indexed（有数据才填写）→impressions→clicks→业务转化。

3. 记录数据平台、采样/延迟、归因窗口、时区、过滤规则及缺失值。null 不等于 0，部署日志不能证明索引，点击不能证明注册或收入。

4. 比较同批上线时间和需求差异，避免把时间先后直接当因果。用最小化事件描述真实行动，不采集正文、个人标识或秘密参数。

5. 输出指标字典、当前可验证基线、数据缺口、观察计划和要回答的决策。用户没要求自动监控时不创建定时任务。

6. 下一步依据结果选择修复已有页面、补证据、延长观察或测试新页面族；数据不足就写尚不能下结论。

## 交付与完成条件

主交付：`16-measurement.md`（指标基线与观察计划）。记录输入版本、证据位置、实际检查、未知与阻塞。

- 每个数字都有来源和时间范围；缺数据仍能交可执行测量计划。
- 指标关联具体业务结果与决策，不承诺固定排名提升。

若项目已有 `project.json` 进度记录，只有完成条件有证据时才更新本步骤为 complete；缺口写 blocked，未实测写 not_checked，不把个人学习勾选当工程证据。上游 revision 变化后重查受影响结论。

下一步通常是 `pseo-refresh`，但以用户当前目标和真实缺口为准。未安装下一项时说明缺项；本步骤仍可独立交付，不假装调用成功。
